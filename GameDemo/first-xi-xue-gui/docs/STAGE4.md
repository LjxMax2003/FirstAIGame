## 1. 做了什么

一句话：**把"局内赚的金币"变成"下一局开局就带上的永久加成"，并且这个循环真的能存下来。**

| 环节 | 落点 |
|---|---|
| 金币产出 | 沿用 Step 11 的 `Game.coin_reward()`（击杀 / 时长 / 精英 / Boss / 资源点，胜利 ×1.5） |
| 结算入账 | `Game._finish()` → `MetaSave.add_coins()`（**只此一处**写存档） |
| 存档 | `scripts/MetaSave.gd`（autoload）→ `user://save.json` |
| 买永久属性 | `scripts/ui/ShopUI.gd` + `scenes/ui/ShopUI.tscn`（5 条线） |
| 生效率 | `Stats.effective_at()` = 局内被动 × 局外乘数，`Game._ready` 时就是新基线 |
| 复活 | `Game._try_revive()`，血量归零时消耗一次，满血 + 3 秒无敌，本局继续 |

五条成长线（价格与步长逐条照抄 `params.json → meta_shop.tracks`）：

| 线 | 步长 | 上限 | 价格 | 满级效果 |
|---|---|---|---|---|
| 攻击 `damage` | +3% / 级 | 5 | 200 / 500 / 1200 / 3000 / 7000 | 伤害 ×1.15 |
| 生命 `max_hp` | +10% / 级 | 5 | 150 / 400 / 1000 / 2500 / 6000 | 上限 ×1.50 |
| 冷却 `cooldown` | −3% / 级 | 5 | 300 / 700 / 1600 / 4000 / 9000 | 冷却 ×0.85 |
| 磁力 `magnet` | +10% / 级 | 3 | 100 / 300 / 800 | 吸附 ×1.30 |
| 复活 `revive` | +1 次 / 级 | 2 | 2500 / 8000 | 本局多 2 条命 |

全表总价 **49,250**。

## 2. 六个关键决定

### 2.1 Meta 只"乘"不"加"，且自成第二乘区

局内被动是 0..5 的固定档位（`Stats.value_at`），Meta 是全局乘数：

```
最终值 = Stats.value_at(key, lv) × MetaSave.mult(key)
```

这么定的原因不是"实现方便"，而是三条约束同时要求它：

1. **不能撑破局内上限。** 如果 Meta 走加法塞进 `value_at`，5 级上限就得重算，数值表全废。
2. **不能让某件被动变成"必选"。** `params.json growth_rules` 明确"同区内加算、区间乘算"；Meta 是独立乘区，所以它抬高的是**所有构筑的基线**，而不是把"伤害"这条线推到唯一解。
3. **必须明显弱于进化。** `meta_shop._note` 给了硬上限：Meta 满级总乘数 1.15 × 1.176 = **1.35**，远低于单把武器进化的 **2.4**。否则"刷金币"会盖过"局内 Build"这个主玩法——那就本末倒置了。

测试直接断言了这条上限（`meta 满级总伤害乘数 ×1.353 ≈ 1.35`）。

### 2.2 `params.json` 的 `might` 改名成 `damage`

`params.json` 里 Meta 这条线的 id 是 `might`（攻击 +3%）。但**局内管线里的 `might` 是"受到接触伤害 −7%"的减伤**（`Stats.value_at("might", lv)`）。

同名不同义。如果照抄 id，代码里会出现 `stats["might"]` 一处当增伤、一处当减伤，这是迟早要出事的坑。所以 Meta 这条线改叫 `damage`，和局内伤害被动同一条**乘区语义**、不同**乘区层级**。

### 2.3 存档单独一个 autoload，不塞进 `GameManager`

`GameManager.stats` 是**本局**数值，每局 `reset()` 清空；金币和永久等级要活过重开、活过退出进程。

混在一起的经典 bug 是"重开一局把玩家花钱买来的加成清掉了"。分开之后，`reset()` 只碰 stats，`MetaSave` 只碰存档，各自的生命周期一目了然。

顺带改了 `GameManager.reset()`：字典改从 `Stats.make_base()` 生成，不再手抄一份。手抄的那份在加入 Meta 之后一定会漏掉加成——这正是"买了 Power Up 却没生效"的典型成因。

### 2.4 商店只从结算界面进，不放暂停菜单

Meta 加成在 `Game._ready` 里算进 `stats`，**中途买的东西本局不生效**。

如果在暂停菜单里也能开店，玩家会买到"攻击 +15%"然后这一局打起来毫无变化——这是 meta 系统最常见的信任崩塌点。所以入口只放结算界面：买完 → 再来一局 → 立刻能感觉到。这也正是"再来一局钩子"该落的位置。

### 2.5 复活的无敌是 3 秒，不是 0.5 秒

复活点必然在怪堆正中。普通受击无敌是 0.5 秒，照搬会让玩家**刚站起来就被同一个人再撞死一次**——2500 金币等于扔进水里。

`MetaSave.REVIVE_INVULN = 3.0`，配合 HUD 青色横幅（区别于进化金 / 危险红），让"钱花在哪了"一眼可见。

### 2.6 入账在 `Game._finish`，且有一次性闸

结算界面是展示层，被测试/调试直接调用时不该顺手改存档。入账只放在 `Game._finish`，并用 `banked` 标志挡住重复调用——否则"最后一击打死 Boss 的同时被小怪撞死"能白拿双份金币。

写盘用**临时文件 + 改名**（`save.json.tmp` → `save.json`）：直接覆盖时中途崩溃会留下半截 JSON，玩家全部局外进度就没了。

## 3. 经济节奏（实测，不是估算）

原先这里是手算的估算。现在有了 `tools/EconomyProbe.tscn`：它**直接积分 `WaveTable` 的刷怪表**、
**直接调 `Game.coin_reward()`**、**直接读 `MetaSave.TRACKS`**，所以改任何一个数都不需要改这个工具。

```bash
godot --headless --path . res://tools/EconomyProbe.tscn
```

### 刷怪与金币

```
刷怪积分 0~1800s：入场 49,083 只 → Boss 战压制扣减 2,600 只 → 实际 46,483 只
精英 174 只 / Boss 3 只 / 全表买满 49,250 金币
```

| 击杀比例 | 胜局击杀 | 金币 | 单线买满（攻击 11,900） | 全表买满（49,250） |
|---|---|---|---|---|
| 0.42（新手） | 19,522 | 4,575 | 2.60 局 | **10.77 局** |
| 0.62（模型均值） | 28,819 | 6,555 | 1.82 局 | **7.51 局** |
| 0.74（熟练） | 34,397 | 7,747 | 1.54 局 | **6.36 局** |

击杀比例取自 `NUM_DESIGN §5.1` 的口径，0.42 / 0.74 作为上下界——单点数字没有意义。

### 中途死亡（钩子成不成立，看的是这张表）

| 存活 | 击杀 | 金币 | 首局能买什么 |
|---|---|---|---|
| 5:00 | 1,381 | **190** | 生命（150）/ 磁力（100） |
| 10:00 | 4,391 | 642 | 攻击·生命·冷却·磁力 首级全开 |
| 15:00 | 8,824 | 1,347 | 同上 |
| 20:00 | 14,776 | 2,201 | 同上（复活还差 300） |
| 25:00 | 21,280 | 3,202 | 加 复活 Lv1（2,500） |

**结论：钩子在第一次死亡就成立。** 哪怕只活 5 分钟，190 金币也够买下生命 Lv1 + 磁力 Lv1。
这是设计要的效果——第一局不该是"白跑"。

|---|---|---|---|
| 磁力 | 1,200 | **0.18 局** | 100 |
| 生命 | 10,050 | 1.53 局 | 150 |
| 复活 | 10,500 | 1.60 局 | 2,500 |

### 一个必须说清的口径冲突

`params.json → meta_shop.coins_per_kill = 0.05`，但 Step 11 落地的 `coin_reward()` 用的是 **0.12**。
两条口径并排算同一局：

| 口径 | 胜利局金币 | 全表买满 | 对 `reach_run = 10` 的偏差 |
|---|---|---|---|
| params 的 0.05 | 3,528 | 14.0 局 | **慢 40%** |
| 实装 0.12 | 6,555 | **7.5 局** | **快 25%** |

**结论：不改。** 实装的 0.12 反而比 params 的 0.05 更接近设计目标 `reach_run = 10`
（0.05 会拖到 14 局，对一个 demo 太长）。这是一个**有数据支撑的保留决定**，不是"忘了对齐"。
`EconomyProbe` 会把这段对照直接打印出来，以后再有人翻到 `coins_per_kill: 0.05` 时不用重新推一遍。

### 两个观察（没有改，留给下一轮决策）

1. **磁力线几乎是免费的**：全表 1,200 金币 = 0.18 个胜局。玩家不需要"选择"，顺手就买满了。
   如果要让它成为决策，得把首级价格抬到"第一局买不起"的量级（> 200）。
2. **7.5 局买满 = 商店会被掏空。** 对一个 demo 是好事（玩家能看到全部内容），
   但作为长期留存循环，后面没有消耗口（`params` 未来的 Reroll/Banish、新角色解锁可以接这里）。

## 4. 测试：55 项新增，以及两个"陈年"假失败的根治

新增用例覆盖：表结构与 `params.json` 对齐 / 买不起不扣钱 / 满级闸门 / 乘数与总上限 / 买完 stats 真的变 / 与局内被动乘算 / 复活全链路 / 入账与防重复 / 商店 UI 三种按钮态 / 关店后的暂停还原 / 跨局持久。

顺手治了**两个与 Step 12 无关、但被本轮改动放大**的测试缺陷——都不是产品 bug，是测量方法错了：

**① 同屏密度断言会飘（实测 73~165）。**
同屏数 = 刷怪率 − 击杀率，而击杀率取决于"自动选卡抽到了什么"。一边自动选卡一边测密度，等于让断言去赌抽卡运气，今天过明天挂。
`seed()` 救不了：`randf` 的调用次数受帧时序影响，同一颗种子两次跑结果仍不同（实测 164 vs 111）。
修法是**把构筑钉死**（鞭弧 Lv2 + 光环 Lv1、被动全 0）再测——密度断言不该由运气决定。修完稳定在 146~165。

**② 升级弹窗抢暂停锁，导致"恢复游戏"假失败。**
升级优先级高于暂停菜单（Step 5 定的设计，正确）。但只要任何用例在等待期间"恰好攒够经验"，整树就暂停，接下来"武器还在开火吗""恢复游戏了吗"全部假失败。
修法是在 `_prep()` 里统一**冻结经验条**（`xp_next = 2^30`），想测升级本身的 Step 5 显式传 `freeze_xp = false` 自己掌控时机。这一条消掉的是一整类 flake，不是单个用例。

## 6. ⚠️ 没做到的（如实记录）

1. **"买完明显变强"的体感未验证。** 单线满级只有 +15%（攻击）/ ×1.5（生命），是 `params.json` 为了"不盖过局内 Build"主动压低的。数值上确实变强了（有测试），但 15% 在操作体感上是否够"明显"，**必须真人试玩才能回答**。
2. **经济节奏是"算准了"，但没有"玩准"。** §3 的数字来自刷怪积分 + 真实结算函数，可信度比手算高得多；但里面的**击杀比例 R 仍取自数值模型（0.42~0.74）**，不是真人打出来的。真人的 R 落在哪一档，只能靠试玩。
3. **复活在 Boss 战中的体验未验证。** 当前只给 3 秒无敌、不清场，理论上"复活即被围"的观感可能很差。
4. **没做多存档槽 / 云同步 / 作弊校验。** `save.json` 是明文 JSON，本地单机场景下可接受。
5. **`user://save.json` 会跨测试与实机共享。** 自动化测试已做"备份 → 清零 → 跑 → 还原"，但如果你手动删档，进度会归零（没有二次确认，这是刻意的：单机 demo 不做防误删弹窗）。
